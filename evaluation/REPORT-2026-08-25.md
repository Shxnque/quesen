## Confirmed strengths (evidence)

- **Determinism holds.** Identical inputs → identical `decision`, `risk_score`,
  and `input_snapshot_hash` across repeated calls. The `sk_sandbox`/1 launch case
  reproduced hash `8f5a847a…` — the *same* hash recorded in the 2026-08-16
  independent evaluation. Determinism is stable across keys and weeks.
- **Decisions match published thresholds** on all 24 swept inputs (`SKIP≥0.65`,
  `REVIEW≥0.35`, else `PROCEED`). No drift between `/version` and `/validate`.
- **Monotonic where it must be:** risk is non-decreasing as scam keywords rise
  (`0.94→1.0…`) and as the domain gets younger (`0.475→0.744→0.826→1.0…`).
- **Robust to adversarial input:** out-of-range (`engagement>1`, negative age/scam)
  and wrong types → `422`; an injection payload in `client_request_id`
  (`'><script>… OR 1=1; DROP TABLE keys;--`) → `200` echoed **harmlessly**;
  unknown extra fields → `422` (schema is closed); huge numbers and an empty body
  → graceful `200`. **No `500`s under any probe.**
- **Security boundary intact:** no key → `401`, bad key → `401`, sandbox key on
  admin `/stats` → `401`.
- **`simulate` is side-effect-free:** threshold overrides return `200` with a
  baseline-vs-simulated delta and named rules (`R1: New domain (<=30d) + unusually
  high engagement (>=0.50)`, `R3: scam keywords + high engagement`), and engine
  weights are unchanged before/after — confirming sandbox semantics.
- **`report` feedback works:** valid outcome (`OK`) → `200`; invalid outcome → `422`.
- **On-chain enrichment reachable:** a real Ethereum contract returns a populated
  `onchain_enrichment` envelope; a junk address is handled gracefully (`200`, no `500`).

## Finding (real — for the engine owner to adjudicate; do NOT tune to hide)

**F1 · `risk_score` is non-monotonic in `engagement_ratio` at the low end.**
With `domain_age_days=3, scam_keyword_count=1`, sweeping engagement produced:

| engagement_ratio | 0.02 | 0.20 | 0.50 | 0.80 | 0.99 |
| --- | --- | --- | --- | --- | --- |
| risk_score | **0.7897** | **0.7267** | 1.0 | 1.0 | 1.0 |

Raising engagement from `0.02` → `0.20` **decreased** risk (0.7897 → 0.7267)
before the ≥0.50 "high-engagement" rule (`R1`) spikes it to `1.0`. Because the
engine is deterministic, this is a **reproducible engine behaviour**, not noise.

- **Most likely benign explanation:** engagement contributes via *buckets/rules*,
  not linearly, and *very low* engagement is itself a mild signal (dead/bot-seeded
  launch), so the curve is U-shaped rather than monotonic.
- **Why it still matters:** a caller who assumes "more engagement ⇒ never less
  risk" will be surprised. Either (a) document that engagement risk is
  non-monotonic by design, or (b) if unintended, treat as an implementation
  defect in the engagement sub-score. **This report does not change any threshold
  or weight** — that decision belongs to the engine owner with the private engine.

**Secondary observation (LOW):** for USDC (`0xA0b8…eB48`) the `onchain_enrichment`
envelope returned with `has_code`, `source_verification.is_verified`, and
`contract_age_days` all `null`. The envelope is present and the call is graceful,
but the enrichment probe appears **degraded/unconfigured** in production (likely a
missing explorer/RPC key), so on-chain signals may not be contributing. Worth a
health check on the on-chain probe credentials.

## Coverage verdict

See the [Domain Evaluation Matrix](./README.md#the-domain-evaluation-matrix-honest-coverage-assessment).
Quesen robustly covers **~3 of the 16** directive domains (autonomous-agent
go/no-go, on-chain transaction-target validation, adversarial-input robustness),
partially covers ~5, and **cannot express ~8** (tool authz, prompt injection,
KYC, data access, privilege escalation, malicious tool calls, supply-chain,
general instruction analysis) — because the input contract has no fields for them.

## Recommendations (evidence-driven, ordered)

1. **Adjudicate F1** on the private engine: document non-monotonic engagement as
   intended, or fix the engagement sub-score. Add a determinism+monotonicity
   golden test so it can't regress silently.
2. **Fix or disable on-chain enrichment credentials** so the envelope is not
   returned with all-`null` probe fields for known-verified contracts.
3. **Decide the contract-extension question** before marketing multi-domain
   security: ship a typed generic-context schema (or per-domain schemas) if the
   tool-authz / prompt-injection / data-access domains are strategic — otherwise
   position Quesen precisely as a *deterministic token/launch + on-chain risk
   oracle for agents*, which is what it verifiably is today.
4. **Build a labelled corpus** (known scams vs known-legitimate launches) to turn
   the false-positive / false-negative rows from "partial" into measured numbers.
